# 호텔 신원 확인 — 표준 절차 (정본)

**날짜**: 2026-08-01
**계기**: 대표님 지적 — *"호텔 매칭은 아고다 API 연결이 아니고, 우리가 받아둔 호텔 DB하고 체크해야 되는 거 아니야?
우리 자체 DB에 보관해서 사용하기로 했잖아. 이렇게 안 하면 할 때마다 불러와야 되는 거 아니야?
… 이 문제가 생길 때마다 네가 체크하고 하는 방식이 계속 달라지는 것 같다고 느껴져."*

**대표님 말씀이 맞다.** 이 문서가 없어서 매번 그때그때 다른 방법으로 처리했다.
앞으로 호텔 신원을 확인할 때는 **이 문서의 순서만 따른다.**

### 1-1. 문서와 실제가 다르다

## 2. 원칙 (이것만 따른다)

### 원칙 ① 아고다 API 는 「채울 때」만 부른다. 「찾을 때」는 안 부른다

```
호텔을 찾는다  →  우리 DB(agoda_inventory) 에서 찾는다
없다           →  그 도시 재고를 «한 번» 채운다 (아고다 호출)
                  → 그다음부터는 우리 DB 에서 찾는다
```

**매칭할 때마다 아고다를 부르지 않는다.** 유료로 올린 DB는 그러라고 있는 것이다.

### 원칙 ② 신원 확인은 이 순서로 한다 (D-071 좌표 원칙 유지)

```
1. 아고다 번호(hid)가 같은가        → 같으면 같은 호텔. 끝.
2. 좌표가 50m 안인가                → 같은 호텔로 본다 (D-071)
3. 이름이 매우 비슷한가             → 사람이 확인한다 (호텔 메뉴 [확인함])
4. 그래도 모르면                    → 「모른다」고 표시한다. 지어내지 않는다.
```

### 원칙 ③ 우리 번호(`hotel_code`)가 주민번호다

아고다 번호는 **남의 번호**다. 바뀔 수도, 없어질 수도 있다.
우리 번호(`hotel_code`)를 붙여두고, 아고다 번호는 **딸린 정보**로 보관한다.
이래야 나중에 아고다 말고 다른 곳을 붙여도 우리 자료가 안 깨진다.

### 원칙 ④ 없는 것은 「없다」고 적는다

영문명을 모르면 빈칸으로 둔다. 추측해서 넣지 않는다.
빈칸은 「아직 안 채웠다」는 신호이고, 채우는 봇이 그걸 보고 일한다.

## 3. 그래서 무엇을 고쳐야 하나 (순서)

### ① `agoda_inventory` 를 콘텐츠 도시까지 채운다 — **가장 급함**

지금 12개 도시뿐이다. **콘텐츠를 만드는 도시는 전부 있어야 한다.**
없으면 그 도시 콘텐츠는 매번 오늘 같은 일이 난다.

- 채우는 단위 = **도시 1곳**(아고다는 도시 단위로 준다)
- 한 번 채우면 끝. 매번 안 부른다.
- 우선순위 = **콘텐츠가 나갔거나 나갈 도시** → 그다음 예약 많은 도시

### ② `hotels` 에 아고다 번호를 잇는다

지금 **0건**이다. 좌표는 3,243개 있으니 **좌표로 이을 수 있다**(원칙 ②-2).

### ③ 발행하면 저절로 이어지게 한다

원고가 지목한 `hid_top1/2/3` 를 발행 시점에
재고에서 찾아 → 호텔 장부에 붙이고 → 영문명·성급·좌표를 채운다.
**없으면 그 도시 재고를 먼저 채운다.**

## 7. 🔴 TOP1·TOP2·TOP3 는 「순서」가 아니라 「글자」로 정한다 (2026-08-01)

> 대표님: *"호텔이름 TOP1, TOP2, TOP3 잘못 넣으면 안됨. 추후 200달러 유료고객 호텔에게 잘못된 정보를 주면 우리 사업에 큰 문제가 생겨. 임시처리 방식으로 일하면 항상 추후에 문제가 커져."*

### 무엇이 잘못돼 있었나

링크가 **본문에 나온 순서**대로 `hid_top1 → hid_top2 → hid_top3` 에 들어가고 있었다.
그런데 **우리 원고는 탑쓰리부터 소개한다**(탑쓰리 → 탑투 → 탑원).
그래서 **정확히 거꾸로** 박혔다.

| 원고 | 저장돼 있던 값 |
|---|---|
| TOP3 = JR 타워 (65806) | hid_top**1** = 65806 |
| TOP2 = ANA (9066914) | hid_top2 = 9066914 |
| TOP1 = 프리미어 츠바키 (10568197) | hid_top**3** = 10568197 |

**발행된 원고 4건 전부** 뒤집혀 있었고, **클릭 추적표(R코드)의 순위도 같이 뒤집혀** 있었다.
이대로 유료 호텔에게 성과를 보고하면 **TOP3 호텔에게 「TOP1 으로 소개됐다」고 거짓말**을 하게 된다.

### 규칙 (`api/_lib/hotel-rank.js`)

**① 순위는 원고에 적힌 글자로 정한다.** `탑원·탑투·탑쓰리` / `TOP1·TOP2·TOP3` / `1위·2위·3위`
**② 링크의 순위 = 그 링크 바로 앞에 나온 순위 글자.** 순서를 세지 않는다.
**③ 교차 확인**: 챕터 줄(`00:10 TOP3 …`)과 본문(`탑쓰리, …`)을 둘 다 읽는다. 영문명은 아고다 상세링크 주소 조각에서 얻는다(`jr-tower-hotel-nikko-sapporo` → `JR Tower Hotel Nikko Sapporo`) — 주소는 아고다가 만든 것이라 사람이 오타를 내도 틀리지 않는다.
**④ 1·2·3 이 각각 정확히 하나씩 안 나오면 저장을 거부한다.** 🔴 애매하면 **추측해서 넣지 않는다.** 틀린 자료가 빈칸보다 나쁘다.
**⑤ 문장을 이름으로 오인하지 않는다.** 「를 추천해 드릴게요!」 같은 줄은 버린다.

### 검증 결과 (2026-08-01)

발행 원고 4건 전수 적용 — **4건 모두 순위 확정 성공**, 이름·영문명도 정확히 추출.
뒤집혀 있던 `publications` 4건과 `content_clicks` 8줄을 **원고 기준으로 정정 완료**.

### 앞으로

- 링크를 저장할 때 `resolveRanks()` 가 순위를 정한다. **못 정하면 저장이 막힌다.**
- 붙인 순서와 원고 순위가 다르면 **원고를 따르고**, 화면에 「원고 기준으로 저장했습니다」라고 알린다.
- 🔴 **원고 형식이 바뀌면 이 규칙부터 확인한다.** 순위 글자가 사라지면 저장이 막히므로 조용히 틀리지는 않는다.

## 8. 지역 성급 분포의 «전체» 는 아고다 호텔 파일로 센다 (2026-08-01)

> 대표님: *"지역의 성급분포에 전체 호텔의 갯수가 맞는거야? 호텔db를 넣었으니깐 정확하게 표시할 수 있는 거 아니야? 실제로 전체 몇 개가 있고 우리는 몇 개를 성급별로 소개했는지 파악할 수 있는 부분이잖아."*

### 무엇이 잘못돼 있었나

분모를 `agoda_inventory` 에서 세고 있었다. 그 표는 **도시당 100~200개만** 담겨 있다.
그래서 **우리가 전체보다 많은** 말이 안 되는 수치가 나왔다.

| 하카타 | 예전 | **지금** |
|---|---|---|
| 전체 | 73곳 | **333곳** |
| 우리 | 89곳 (**120~450%**) | 89곳 (**27%**) |
| 5성 | 전체 5 · 우리 6 (120%) | 전체 30 · 우리 6 (**20%**) |
| 4성 | 전체 16 · 우리 20 (125%) | 전체 34 · 우리 20 (**59%**) |
| 3성 | 전체 39 · 우리 40 (102%) | 전체 157 · 우리 40 (**25%**) |

이제 **「이 동네에 3성이 157곳 있는데 우리는 40곳만 안다」** 처럼 읽을 수 있다. 이게 원래 이 화면의 목적이었다.

### 규칙

- 분모 = **`agoda_hotel`** (아고다 호텔 파일 · 52만 건). `agoda_inventory` 는 사진·후기용이라 분모로 쓰지 않는다.
- 조인은 **좌표로만** 한다(`agoda_hotel` 에 city_id 가 없다). 네모로 먼저 거르고(색인) 반경 **800m** 로 확정한다.
- 🔴 **분모가 0이면 0이라고 둔다.** 우리 것으로 채우지 않는다 — 그러면 「전체=우리」가 되어 미개척이 0으로 보인다.

### 남은 예외 (2026-08-01 실측)

- **서울 4개 구 · 교토 사쿄구 · 다낭 · 타이베이 1곳 = 분모 0** — 아고다 파일에 그 좌표 근처 호텔이 없다.
  🔴 **한국은 아고다 한국어 파일에 국내 호텔이 아예 없다**(0건). 영어(EN) 파일 확인이 필요하다.
- **도쿄 긴자 5성** 만 아직 우리(8) > 전체(6). 반경 800m 밖 호텔이 우리 장부에 있는 경우다. 1건뿐.

## 9. 주소·좌표는 아고다 파일에서 얻는다 — 구글은 최후 (2026-08-02)

> 대표님: *"구글 이름으로 못 찾았다는데, 우리가 받은 아고다DB에 위치값들이 있잖아. 거기 GPS 값도 있잖아. 구글 체크는 한 달에 한계가 있어서 다른 방식으로 하기로 한 거 아니야?"*

맞다. `SYSTEM_MAP §4` 에 **「아고다 1차 · 구글 최소」**라고 이미 적혀 있었다.
그런데 화면은 여전히 *"구글이 이름으로 못 찾았습니다"* 라고 말하고 있었다.

### 실태 (실측)

| | |
|---|---|
| 우리 장부 좌표 | **3,243 / 3,252 (99.7%)** — 이미 아고다 파일로 채움 |
| 그런데 **주소** | 1,457곳이 비어 있었다 |
| 주소가 없으니 | **「구」를 못 붙인다** → 도쿄 233곳 중 77곳이 지역 미배정 |
| 아고다 파일 주소 | **99%** 있다 (일본 93,759 / 94,677) |

**이름이 안 맞아서 못 찾았을 뿐이다.** 좌표로 대면 **0m** 로 정확히 붙는다.

### 규칙

**① 이름으로 찾지 않는다. 좌표로 찾는다.** (D-071 과 같은 원칙)
- 아고다 이름과 우리 이름은 다를 때가 많다 (`Hotaku HOTEL` ↔ `호타쿠 호텔`)
- 좌표 **50m 안**이면 같은 호텔로 본다

**② 구글은 부르지 않는다.** 아고다 파일에 없을 때만 마지막으로 쓴다.
- 구글 Places 는 한 달 한도가 있다. 아고다 파일은 **무료·무제한**이다
- `hotel-addr-fill` 봇(매시 40분)이 **구글 호출 0** 으로 채운다

**③ 아고다 번호도 같이 잇는다.** 우리 장부에 아고다 번호가 **0건**이었다(2026-08-01 실측).
주소를 채울 때 그 호텔의 아고다 번호도 함께 박는다.

**④ 못 찾으면 그대로 둔다.** 지어내지 않는다(원칙 ④).

### 흐름

```
아고다 호텔 파일(52만 건 · 좌표·주소·성급)
        │
        ├─ [hotel-addr-fill] 매시 40분 ─→ 좌표 50m 로 대고 주소·아고다번호 채움 (구글 0)
        │                                     │
        │                                     ▼
        ├─ [hotel-district-fill] 매일 03시 ─→ 주소에서 「구」를 뽑아 지역 배정
        │
        └─ [hotel-fill] 매시 30분 ────────→ 새 콘텐츠에 나온 호텔을 우리 DB 에 등록

구글 Places = 아고다 파일에도 없을 때만 (한 달 한도 있음 · 지금 사실상 안 씀)
```
