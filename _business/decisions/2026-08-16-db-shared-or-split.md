# D-095 — travelwinners.shop 의 DB, 따로 쓸 것인가 같이 쓸 것인가

**날짜**: 2026-08-16 · **판단**: 클로드(기술) · **확인**: 이지형 대표님 · **상태**: 확정

## 대표님 질문
*「우리가 커질 거니깐. 기존에 같이 쓰면 호출의 문제가 있잖아. 이 부분을 정확하게 판단해라.」*

## 결론
> **DB(Supabase 프로젝트)는 하나로 같이 쓴다. 코드·배포·장부·레인은 따로 쓴다.**
> **DB 를 나눠도 호출 문제는 안 풀린다 — 오히려 늘어난다.**

## 왜 — 「호출 제한」의 정체는 세 가지이고, 셋 다 DB 분리로 안 풀린다
| 무엇 | 한도 | DB 를 나누면? |
|---|---|---|
| 우리가 만든 창구 `api/ops/*` | 120회/시간 | **안 바뀜.** 이건 클로드·관리자용 문이지 사이트용이 아님. 레인만 나누면 됨 |
| Supabase 자체 성능 | 초당 수백 쿼리 가능 | 지금 병목 아님. 화면을 **정적 파일**로 구우면 손님 트래픽은 DB 에 **0회** 도달 |
| 아고다 API | 90회/시간 | 🔴 **나누면 나빠짐.** 창고가 둘이면 같은 호텔을 두 번 물어 한도를 두 배로 먹음 |

핵심: 대표님이 걱정한 «호출»은 대부분 **아고다** 이야기이고, 그건 **창고를 합쳐야** 줄어든다.

## 따로 / 같이 (확정)
| 따로 쓴다 | 같이 쓴다 |
|---|---|
| GitHub 레포 (이미 분리됨) | **Supabase 프로젝트 1개** |
| Vercel 프로젝트·도메인 | 호텔 명부 `hotel_master` |
| 장부 이름표 `shop_*` / `blog_*` / `pkg_*` | **가격 창고**(아고다 조회 결과) |
| 창구 레인(사업별 상한) | 수집 봇 · 회원 · 이벤트 · 클릭추적 부품 |
| RLS 정책 | 관리자 화면 뼈대 |

## 🔴 나눠야 할 때 (미리 정해둔 신호)
하나라도 켜지면 그때 나눈다. 지금은 아니다.
1. **패키지 결제·개인정보(여권·카드)가 들어올 때** → 그건 무조건 별도 DB. 마케팅 자료와 섞으면 안 됨
2. 한 사업이 DB 사용량의 **60% 이상**을 먹을 때
3. Supabase CPU·커넥션 경고가 **반복**될 때
4. 사이트 30개 초과 → 나누는 게 아니라 **읽기 전용 사본**을 늘린다

## 지금 반드시 지킬 3가지 (이것만 지키면 하나로 충분)
1. **이름표 분리 + RLS** — `shop_*` 표는 shop 만 건드림
2. **창구 레인 분리** — shop 이 폭주해도 블로그 발행이 안 멈춤
3. **화면은 정적 굽기** — 손님은 DB 에 안 간다. 사이트 100개여도 DB 호출 0 증가

## 되돌리기
나중에 나누는 건 쉽다(표 이름이 이미 갈라져 있으므로 통째로 옮기면 됨). 반대로 **합치는 건 어렵다**. 그래서 지금은 하나로 두고 신호를 기다린다.
