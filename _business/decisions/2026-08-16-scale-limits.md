# D-094 — 사업이 늘어날 때의 한도 설계

**날짜**: 2026-08-16 · **결정자**: 이지형 대표님(문제 제기) + 클로드(설계) · **상태**: 확정
**정본 반영**: `docs/ARCHITECTURE.md` §4-B

## 왜 나왔나
대표님: *「지금처럼 푸시하고 자료 검색하고 개발하면 여기도 한도가 걸리잖아. 우리는 계속 개발작업을 한다고 앞으로 여러 개의 사이트 및 블로그를 만들어야 된다. 하나만 생각하지 마라 복합적으로 생각해야 된다.」*

ARCHITECTURE §4(새 사업 표준 6단계)에는 **사업을 만드는 법**만 있고 **사업이 늘 때 한도가 어떻게 되는가**가 빠져 있었다.

## 발견한 함정
사업마다 문에 90회/시간을 주는데 **전체 상한 120회/시간은 고정**(DB 보호선·2026-07-22 사고로 절대 불변).
→ 사업 2개면 요구 180 vs 천장 120, 4개면 360 vs 120. **사업이 늘수록 각자 몫이 줄어든다.**
실측: 2026-08-16 시안 기획 한 건에 `github-commit` **8회/30회**를 소모. 사이트 4개를 동시에 개발하면 그날로 막힌다.

## 결정 — 새 원칙 한 줄
> **사업이 늘어도 «문 두드리는 횟수»는 늘지 않게 만든다**

### 늘려도 되는 것 / 절대 늘리면 안 되는 것
- 늘려도 됨: 도메인 · 레포 · Vercel 프로젝트 · 이름표 prefix · 신호등 한 줄
- 절대 안 됨: DB 인스턴스 · 봇 종류 · 외부 API 계정 · 규칙 문서

### 병목 5개와 처방
1. **DB 창구 120/h(천장)** — 올리지 않는다. 새벽에 JSON 으로 구워 CDN 에 올리고 **화면은 파일을 읽는다**. 사업 10개여도 DB 호출 0 증가
2. **저장 창구 30/h** — 묶음 커밋(한 번에 파일 N개) · 초안은 커밋 안 함 · 배포 확인 폴링 축소
3. **아고다·구글 90/h** — 창고 1개 + 수집 봇 1개. 새 사이트는 꺼내 쓰기만 → 외부 호출 **0 증가**
4. **GitHub Actions 분** — 봇을 사업마다 복제하지 않고 한 봇이 사업 목록을 순회
5. **Vercel·Supabase 요금** — 돈으로 푸는 것. 지금 병목 아님(월 $45). 여기서 아끼려다 위 4개를 망가뜨리지 않는다

### 착각 방지
120회/시간은 **관리·개발용**이다. 손님 화면은 이 문을 쓰지 않는다(정적 파일 또는 Supabase 직결+RLS).
손님이 늘어서 막히는 게 아니라 **우리 개발이 막힌다.**

### 사이트 공장
6단계를 매번 손으로 하지 않는다. **템플릿 레포 1개**를 복제하고 이름·도메인·CID 만 바꾼다.

### 측정
점검판(ops.html)에 창구별 **남은 횟수·사용률** 표시, 80% 경고. 지금은 막히고 나서야 안다.

4. 새 사이트 템플릿 레포
