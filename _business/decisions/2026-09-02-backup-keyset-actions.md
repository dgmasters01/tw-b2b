# D-102 · 백업은 「열쇠순으로 읽어」 GitHub Actions 에서 돌린다

**날짜** 2026-09-02 · **상태** 확정 · **분류** infra
**관련** `BUSINESS-MAP §5-C`(백업과 복구) · `§5-D`(요금제와 되는 값) · `GAPS BJ`(33일 공백) · `CRON-PLAN §10-H`

---

## 무엇이 문제였나

백업이 2026-07-31 이후 **33일 동안 한 번도 성공하지 못했다**.
크론은 매일 8번 돌았지만 끝까지 간 적이 없어 `backup_progress` 기록이 **0건**이었다.

그동안 원인을 «시간이 모자라서»로 봤다. 그래서
- 08-30 : 회차를 나누는 구조로 고침 → 여전히 실패
- 09-02 : `maxDuration` 을 300 → 800 으로 올림(Vercel Pro) → **여전히 실패**

## 🔴 실측 — 시간이 아니라 「읽는 방법」이 문제였다

옛 백업기는 표를 `ORDER BY ctid LIMIT 2000 OFFSET n` 으로 읽었다.
`ctid`(행의 물리적 자리)에는 **색인이 없다.** 그래서 한 쪽을 읽을 때마다
301만 행을 **통째로 정렬**했다.

| 읽는 방법 | hotel_master 한 쪽 | 301만 행 환산 |
|---|---|---|
| `ORDER BY ctid` + OFFSET (옛 방식) | **16.4초** / 2,000행 | **약 6.9시간** |
| 열쇠순(PK) 2,000행 | 2.8초 | 약 70분 |
| **열쇠순 20,000행 (새 방식)** | **4.5초** | **약 13분** |

→ 1,508쪽 × 16.4초. **300초로도 800초로도 끝날 수 없는 구조였다.**
→ 그래서 «표 CSV 만들기 vs GitHub 커밋» 중 어디가 병목인지는 애초에 물을 필요가 없었다.
   **커밋에 도달한 적이 없다.**

## 함께 드러난 것 두 가지

```
① MAX_ROWS_PER_TABLE = 200000 이 코드에 박혀 있었다.
   성공했더라도 hotel_master 는 301만 행 중 20만 행(6.6%)만 백업되고
   나머지는 «조용히» 버려졌을 것이다. 백업이 됐다고 믿는 게 더 위험하다.
② hotel_master CSV 실측 용량 = 1.03GB (2,349MB 는 색인 포함 수치였다).
   GitHub 은 파일 한 개가 50MiB 초과면 경고, 100MiB 초과면 거부한다(공식 문서).
   → 한 파일로는 애초에 불가능했다. 조각내야 한다.
```

## 결정

```
① 읽는 방법 — 표마다 칸 하나짜리 기본열쇠(PK)를 찾아
   where 열쇠 > 마지막값 order by 열쇠 limit 20000 으로 이어 읽는다.
   🔴 OFFSET 은 쓰지 않는다. 열쇠 없는 표 11개는 자리 범위(ctid range)로 자른다.

② 일터 — GitHub Actions (.github/workflows/db-backup.yml · 매일 UTC 18:10 = KST 03:10)
   13분은 Vercel Pro 상한(800초 = 13분)에 너무 붙어 있다. 표가 늘면 바로 다시 죽는다.
   Actions 는 6시간이고, tw-b2b 는 공개 저장소라 실행 시간이 무료·무제한이다(공식 billing 문서).
   → 월 0원.

③ Vercel 크론은 제거 — 매일 8회 × 최대 800초가 33일간 전부 실패하며
   Pro 함수 시간을 태우고 있었다. 입구(api/cron/db-backup.js)는 ?dry_run=1 수동 확인용으로만 남긴다.

④ 파일은 40MB 로 자른다 (data/<표>/part-0001.csv).
   열쇠순 정렬이라 자료가 안 바뀌면 파일이 «바이트까지» 같다 → git 이 아무것도 안 쌓는다.

⑤ 창고가 private 이 아니면 봇이 스스로 거부한다. hotels 에 호텔 사장님 연락처 3,185개가 있다.

⑥ 창고 조회는 Supabase 관리 API 로 «직접» 한다. 창구(Vercel)를 거치지 않는다 —
   거치면 두 사업이 나눠 쓰는 시간당 한도(120/h)를 백업 혼자 다 써버린다.
```

## 🔴 규칙으로 남긴다

```
1) «시간 제한에 걸렸다» 고 판단하기 전에 «한 번에 얼마나 걸리는지» 를 잰다.
   한도를 올리는 것은 원인을 찾은 뒤의 일이다. 09-02 에 300→800 을 먼저 해서 하루를 더 썼다.
2) 큰 표를 페이지로 읽을 때 OFFSET 을 쓰지 않는다. 뒤로 갈수록 느려진다.
   색인이 있는 열쇠로 «이어 읽기»(keyset) 한다.
3) 상한(MAX_ROWS 같은 것)을 코드에 박을 때는 «넘으면 어떻게 되는지» 를 같이 적는다.
   조용히 자르는 상한은 백업에서 특히 위험하다.
4) 13분짜리 일을 13분 상한 위에 올리지 않는다. 여유가 2배 없으면 자리를 옮긴다.
```

## 남은 위험 (다음에 볼 것)

```
백업 창고 첫 용량이 약 1.2GB 가 된다.
GitHub 권장은 «1GB 미만이 이상적, 5GB 미만 강력 권장» 이다(공식 문서).
아고다 월 1회 갱신 때마다 hotel_master 전체가 바뀌어 이력이 쌓인다.
-> BUSINESS-MAP §5-C-9 에 «이력 90일» 규칙과 경보선(3GB)을 둔다.
```
