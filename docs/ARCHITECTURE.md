## 4. 새 사업을 시작할 때 (표준 6단계)

앞으로 사업이 늘어도 **이 6개만** 만든다. 매번 구조를 다시 논의하지 않는다.

1. 자기 도메인 (Cloudflare Registrar)
2. 자기 GitHub 레포
3. 자기 Vercel 프로젝트
4. **자기 문 + 자기 열쇠 + 자기 몫(90회)** — `staycurate/api/ops/db-query.js` 복사해서 이름만 바꿈
5. **자기 이름표** (`blog_` 처럼 `ceylon_` · `package_`)
6. 관리실 `_os/status-targets.json` 에 **한 줄 추가** → 신호등 자동 생성

### 창고를 «같이» 쓸지 판단하는 기준 한 줄
> **「한 줄 한 줄을 맞대볼 일이 있나?」**
> 있다 → 같은 창고 (스튜디오↔블로그. 같은 호텔인지 대조해야 함)
> 없다 → **따로.** 문으로 물어보면 됨 (패키지여행·CEYLON 등 대부분)

### 조직(Organization) 은 하나로 모은다
🔴 **조직 분리는 보안 방어선이 아니다.** 로그인 계정이 하나면 조직을 나눠도 같이 털린다.
조직은 «청구서 단위»일 뿐 → 새 사업은 **같은 조직에 새 프로젝트**로. (조직 2개면 기본료 $25 를 두 번 냄)
**프로젝트끼리는 같은 조직 안에서도 완전히 분리된다.** 격리는 프로젝트가 만든다.

## 5. 보안 방어선 5겹

| 겹 | 뚫리면 | 막는 법 | 상태 |
|---|---|---|---|
| 1 | Supabase 로그인 계정 | **2단계 인증(MFA)** | 🔴 **폰 교체 후** (대표님) |
| 2 | `ops` 토큰 (임의 SQL 실행) | 열쇠 분리·권한 축소 | ⏳ 개발 완료 후 (대표님 지시) |
| 3 | 프로젝트 자격증명 | 사업별 프로젝트 분리 | ✅ |
| 4 | 표 잠금(RLS) | 표마다 잠금 | ✅ **77/77** |
| 5 | 코드·배포 | 레포·Vercel 분리 | ✅ |

🔴 **표를 만들면 같은 작업에서 잠근다.** 8/4 에 27개를 잠갔는데 3주 만에 24개가 다시 열려 있었다.
→ 사람이 기억하는 규칙은 반드시 샌다. **점검판에 「안 잠긴 표 N개」 상시 표시.**
```sql
alter table public.새표 enable row level security;
```
- 2단계 인증은 **폰 앱(Authenticator)보다 비밀번호 앱(1Password 등)** 권장. 폰을 바꿔도 따라온다.
- 복구 코드는 반드시 따로 보관. 🔴 Claude 에게 보내지 않는다.

## 6. 대량 적재 안전 규칙 (9시간 무중단 실전 검증)

🔴 2026-07-22 에 대량 적재로 DB가 뻗어 **로그인까지 멈춘** 이력이 있다. 원인은 «파일 크기»가 아니라 **몰아친 속도**였다.

```
① 새 표에 넣는다              지금 쓰는 표는 손도 안 댐 → 서비스 영향 0
② 매 묶음마다 사이트 응답 측정
      4초 초과 → 쉬고 재확인 → 회복되면 계속
      두 번 연속 이상 → 정지
③ 두 문을 번갈아 쓴다          한도 걸리면 상대 문으로
④ 검증 통과 후 이름 바꿔치기(1초)
⑤ 옛 표는 _old_YYYYMMDD 로 보관
```

### 실전에서 배운 것 (다음에 반드시 참고)
- **묶음이 클수록 서버가 편하다.** 4,000행 배치일 때 응답 0.07초. 문을 자주 여닫는 게 부담.
- 단, **긴 소개글이 몰린 구간**은 500~800행으로 줄여야 통과.
- 🔴 503/502 로 **8개 구간이 통째로 빠졌다.** 총량만 봐서는 못 잡는다 → **id 대조로 구멍을 찾아야 한다.**
- 자료에 **널 문자(\x00)** 가 섞이면 삽입 실패. 걷어낸다.

```
[명부층]  hotel_master   H-##### 부여. 세상의 호텔 대장. 읽기만
              │ 각 사업이 «번호만» 참조
   [스튜디오]      [블로그]        [패키지여행]
    hotels        blog_*          ceylon_*
   영업 대상       소개 이력        상품 포함 호텔
```

- 🔴 **번호는 절대 바뀌지 않는다**(영구 식별자 · `HOTEL_MATCH.md` 원칙③).
  명부를 43배로 교체할 때도 기존 69,785곳은 **원래 번호를 그대로 승계**했다.
- 신규 발급은 마지막 번호 다음부터. 2026-08-11 기준 신규는 `H-0070646~`.
- 🔴 **블로그가 소개했다고 스튜디오 영업 명단(`hotels`)에 넣지 않는다.** 두 사업은 별개다.
  (대표님 2026-08-11: *"블로그하고 $200 호텔 사업을 연결해서 해석하지 마라"*)

**실측(10일 기준, 일본)**: 신규 3.8% · 폐업 1.1% · 후기 변동 11%.
단, 자격선(후기 400) 이 뒤바뀐 곳은 0곳 → **평점 때문에 급할 일은 아니다. 진짜 이유는 신규·폐업.**

- 파일 주소는 `agoda_file_source` 표에 보관. 🔴 **확장자는 `.zip`** (`.z` 로 잘못 저장돼 404 로 오인한 적 있음 · 2026-08-11 정정).
- 파일은 425MB(압축) / 1.9GB(CSV) / 3,015,718행 / 39칸.
- 아고다가 주소를 바꿀 수 있다 → 봇이 주소를 눌러보고 죽어 있으면 **점검판 빨간불**. 대표님은 그때만 5분.
- 🔴 **조건을 걸어 일부만 넣지 않는다.** 8/1(15개국)·8/9(6.9만)처럼 조건을 걸면 반드시 부족해져서 또 넣게 된다.
